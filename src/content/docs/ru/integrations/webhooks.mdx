Вебхуки работают в обе стороны:

- **входящие** — HTTP-запросы от внешних систем, которые от имени [API-ключа](/ru/integrations/api-keys) выполняют операции в рабочем пространстве: создают и обновляют задачи, комментируют их, списывают время, публикуют сообщения в чат, создают и обновляют документы;
- **исходящие** — HTTP-запросы, которые «Интабия Платформа» сама отправляет вам, когда в рабочем пространстве что-то произошло.

Оба вида настраиваются в **Настройки → API + Webhooks**. Там же есть раздел **Примеры**: выбираете операцию или событие и реальный объект, и получаете готовое тело запроса с подставленными настоящими идентификаторами.

# Входящие вебхуки

## Формат запроса

Есть два адреса для одного и того же вызова.

Основной — ключ в заголовке `Authorization`:

```bash
curl -X POST 'https://<host>/_webhook/api/v1/webhook/action' \
  -H 'Authorization: Bearer fus_myworkspace_7f3a9c1d2e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 3f29a1d2-6b1a-4e51-9b0a-6a1c9d8e7f21' \
  -d '{
    "action": "issue:create",
    "space": "FUSIO",
    "title": "Sync failing for tenant X",
    "description": "Steps to reproduce:\n1. Open integration settings\n2. Click Sync",
    "assignee": "dev@example.com",
    "priority": "high"
  }'
```

Второй — тот же ключ прямо в пути, для отправителей (например, некоторых no-code сервисов), которые умеют настраивать только URL, без собственных заголовков:

```bash
curl -X POST 'https://<host>/_webhook/api/v1/webhook/k/fus_myworkspace_7f3a9c1d2e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8' \
  -H 'Content-Type: application/json' \
  -d '{"action": "chat:post", "space": "general", "message": "Deploy finished"}'
```

Ключ в пути целиком попадает в access-логи прокси и балансировщиков — используйте этот вариант, только когда заголовок недоступен. У него и лимит частоты запросов строже (см. ниже).

Рабочего пространства в адресе нет: его определяет сам ключ. Точные адреса вашей установки показаны в **Настройки → API + Webhooks → Примеры → Входящий запрос**, оттуда их можно скопировать.

<Image src={exampleIncoming} alt='Пример входящего запроса' inferSize />
 Тело запроса — всегда JSON вида `{ "action": "...", "space": "...", ...поля операции }`; поле `action` определяет, какая операция выполняется, а `space` — это пространство операции в терминах отправителя (идентификатор проекта, задачи, имя канала или тимспейса — свой для каждой операции, см. таблицу ниже).

## Операции

| `action` | Что делает | Обязательные поля | Необязательные поля |
|---|---|---|---|
| `issue:create` | Создаёт задачу | `space` — идентификатор проекта (например, `FUSIO`); `title` | `description` (markdown), `assignee` (email), `priority`, `estimation` (число), `parent` (идентификатор родительской задачи) |
| `issue:update` | Обновляет задачу | `space` — идентификатор **задачи** (например, `FUSIO-42`) | `title`, `description`, `priority`, `assignee` (email или `null`, чтобы снять исполнителя), `status` (имя статуса) |
| `issue:comment` | Комментирует задачу | `space` — идентификатор задачи; `message` | — |
| `issue:time_report` | Списывает время на задачу, а с полем `id` — правит уже списанное | `space` — идентификатор задачи; для создания также `employee` (email), `date` (`YYYY-MM-DD`), `hours` (больше нуля) | `description`; `id` — идентификатор записи времени: если он передан, правятся только присланные поля этой записи |
| `chat:post` | Публикует сообщение в канал | `space` — имя или id канала; `message` | — |
| `doc:create` | Создаёт документ | `space` — имя тимспейса; `title` | `content` (markdown), `parent` (id родительского документа) |
| `doc:update` | Обновляет документ | `space` — id документа | `title`, `content` |

Как резолвятся ссылки:

- **Проект** (`issue:create`) ищется по идентификатору проекта, а **задача** (`issue:update`, `issue:comment`, а также `parent` у `issue:create`) — по своему идентификатору вида `FUSIO-42`.
- **Исполнитель** (`assignee`) ищется по email как верифицированный социальный идентификатор контакта.
- **Канал** (`chat:post`) сначала ищется по id, а если не найден — по имени; если имени соответствует несколько каналов, запрос завершается ошибкой.
- **Статус** (`issue:update`) ищется по имени без учёта регистра среди статусов, доступных типу задач проекта, которому принадлежит задача.
- **Запись времени** (`issue:time_report`): `employee` ищется по email, как и `assignee`; `id` при правке сверяется с задачей из `space` — чужую запись поправить нельзя. Идентификатор записи приходит в ответе на её создание (`reportId`) и в исходящем событии `issue.time_reported`.
- **Тимспейс** (`doc:create`) ищется по имени. А вот **документ** — и обновляемый в `doc:update`, и `parent` в `doc:create` — принимается только как «сырой» внутренний id: у документов пока нет человекочитаемого идентификатора вроде `FUSIO-42`, по которому можно было бы искать по названию.

Значения `priority` (без учёта регистра): `urgent`, `high`, `medium`, `low`, `none` (синоним — `no_priority`).

## Ответ и статус задания

Оба адреса приёма в случае успеха отвечают `202` и телом `{ "jobId": "wh_..." }` — запрос принят и поставлен в очередь, дальнейшая обработка асинхронная.

Проверить статус задания:

```bash
curl 'https://<host>/_webhook/api/v1/webhook/job/wh_1a2b3c4d5e' \
  -H 'Authorization: Bearer fus_myworkspace_7f3a9c1d2e4f5061728394a5b6c7d8e9f0a1b2c3d4e5f60718293a4b5c6d7e8'
```

Ответ:

```json
{
  "jobId": "wh_1a2b3c4d5e",
  "status": "done",
  "createdAt": 1735689600000,
  "result": { "identifier": "FUSIO-142" }
}
```

`status` — `queued`, `done` или `failed`. `result` появляется только при `done` и содержит то, что вернула операция (например, `identifier` у `issue:create`/`issue:update`, `messageId` у `issue:comment`/`chat:post`, `docId` у `doc:create`/`doc:update`). `error` появляется только при `failed` и содержит текст причины. Для проверки статуса подходит любой действующий ключ этого же рабочего пространства, не обязательно тот, которым задание создавалось.

Информация о задании хранится примерно сутки — после этого `GET job/{id}` вернёт `not_found`, даже если задание было выполнено.

## Коды ошибок

Ответ с ошибкой — всегда JSON вида `{ "error": "<код>", "message": "<текст>" }`.

| `error` | HTTP | Что значит |
|---|---|---|
| `unauthorized` | 401 | Ключ не передан, не найден, отозван, истёк или выдан для другого рабочего пространства. Ответ намеренно одинаковый для всех этих случаев, чтобы не подсказывать, какие ключи вообще существуют. |
| `forbidden` | 403 | Ключ не даёт права на операцию из `action` — её нет в списке разрешённых при выпуске ключа. |
| `invalid_payload` | 400 | В теле нет обязательных `action`/`space`, либо `action` не входит в список известных операций. |
| `payload_too_large` | 413 | Тело запроса больше 1 МБ. |
| `rate_limited` | 429 | Превышен лимит частоты запросов. |
| `not_found` | 404 | Задание с таким `id` не найдено (либо создано в другом рабочем пространстве); тот же код — для неизвестного пути. |
| `internal_error` | 500 | Внутренняя ошибка при приёме запроса. |

Проверки идут по порядку, и каждая следующая выполняется, только если пройдена предыдущая: ключ → тело запроса → право на операцию → лимит частоты → идемпотентность → постановка в очередь. Единственное исключение — `413`: слишком большое тело отклоняется до того, как запрос вообще доходит до этой цепочки проверок.

## Лимиты

Частота запросов ограничена скользящим окном отдельно по ключу и отдельно по IP-адресу отправителя — сработавшим считается тот лимит, который исчерпался первым. Значения по умолчанию, запросов за 60 секунд:

- ключ в заголовке `Authorization` — 60;
- ключ в пути `/k/{key}` — 20 (строже: такой ключ целиком утекает в логи);
- IP-адрес — 60.

При `429` в ответе есть заголовки:

- `Retry-After` — через сколько секунд можно повторить попытку;
- `Retry-After-ms` — то же в миллисекундах;
- `X-RateLimit-Limit` — лимит запросов на текущее окно;
- `X-RateLimit-Remaining` — сколько запросов осталось (при `429` — `0`);
- `X-RateLimit-Reset` — момент, когда текущее окно обнулится, в миллисекундах Unix-времени (не в секундах).

## Идемпотентность

Заголовок `Idempotency-Key` — любое уникальное значение на ваш выбор (например, UUID события в вашей системе). Повторный запрос с тем же ключом от того же API-ключа не создаёт новое задание — в ответ снова приходит `202` с `jobId` первого запроса. Идемпотентность привязана к паре «API-ключ + значение `Idempotency-Key`» и хранится около суток; после этого повтор с тем же значением создаст новое задание.

Дедупликация не сверяет тело запроса — если отправить один и тот же `Idempotency-Key` с другим телом, в ответе всё равно вернётся `jobId` самого первого запроса, а не результат обработки нового тела. Выбирайте значение, уникальное именно для конкретного события.

## Поведение при ошибках и повторах

- Ошибки на входе (`401`, `403`, `400`, `413`, `429`) — окончательны. Повторять тот же запрос без изменений бессмысленно: нужно исправить ключ, тело, права или дождаться окончания окна лимита.
- После `202` обработка асинхронная. Если операция сама завершается постоянной ошибкой (например, невалидные ссылки в теле или ключу не хватает прав на нужное пространство), задание сразу помечается `failed`, без повторов — причина видна в `error` через `GET job/{id}`.
- Временные сбои (сеть, недоступность внутренних сервисов) обрабатываются повторами по расписанию: 30 секунд, 1, 2, 4, 8 минут — всего до 5 попыток. Если и после них операция не выполнилась, задание помечается `failed` окончательно.

## События

| Тип | Когда отправляется |
|---|---|
| `issue.created` | Создана задача |
| `issue.status_changed` | Изменён статус задачи |
| `issue.assigned` | Изменён исполнитель задачи |
| `issue.commented` | К задаче добавлен комментарий |
| `issue.time_reported` | На задачу списано время |
| `issue.time_report_updated` | Запись о списанном времени изменена |
| `message.posted` | Опубликовано сообщение в канале |
| `document.created` | Создан документ |

## Тело события

Готовый пример с настоящими идентификаторами собирается в **Примеры → Исходящее событие**:

<Image src={exampleOutgoing} alt='Пример исходящего события' inferSize />

```json
{
  "action": "update",
  "type": "issue.status_changed",
  "actor": "author@example.com",
  "actorUrl": "https://fusion.example.com/workbench/acme/contact/64f10a1b2c3d4e5f6a7b8c8f",
  "url": "https://fusion.example.com/workbench/acme/tracker/FUSIO-123",
  "data": {
    "id": "64f10a1b2c3d4e5f6a7b8c91",
    "identifier": "FUSIO-123",
    "status": "In Progress"
  },
  "updatedFrom": { "status": "Todo" },
  "webhookId": "msg_2f1c9a7b",
  "webhookTimestamp": 1789084800,
  "organizationId": "9c858f36-6b1a-4d3a-8f2e-1a2b3c4d5e6f"
}
```

- `action` — `create`, `update` или `remove`;
- `type` — тип события из таблицы выше;
- `actor` — email автора изменения, `actorUrl` — ссылка на его карточку;
- `url` — ссылка на сам объект: задачу, документ или канал;
- `data` — состояние объекта, `updatedFrom` — прежние значения изменённых полей (только у `update`);
- `webhookId`, `webhookTimestamp` — идентификатор и время доставки, они же участвуют в подписи;
- `organizationId` — идентификатор рабочего пространства.

Значения в событии — те же, что принимает входящий API, чтобы объект можно было сразу отправить обратно: статус приходит **именем** (`In Progress`), исполнитель и автор — **email**, приоритет — именем (`urgent`, `high`, `medium`, `low`, `no_priority`), канал — своим именем в `data.channel`, родительская задача комментария или записи времени — идентификатором в `data.issue`. Если значение разрешить не удалось, в поле останется внутренний идентификатор.

## Подпись

Доставка подписывается по схеме [Standard Webhooks](https://www.standardwebhooks.com/). Заголовки:

| Заголовок | Значение |
|---|---|
| `webhook-id` | Идентификатор доставки |
| `webhook-timestamp` | Время отправки, Unix-время в секундах |
| `webhook-signature` | Подписи через пробел, каждая вида `v1,<base64>` |
| `X-Webhook-Delivery-Id` | Тот же идентификатор доставки, для журналов |
| `X-Webhook-Attempt` | Номер попытки, начиная с 0 |

Проверка: берётся строка `{webhook-id}.{webhook-timestamp}.{тело запроса}`, считается HMAC-SHA256 с ключом — это байты секрета после префикса `whsec_`, декодированные из base64 — и результат в base64 сравнивается с одной из подписей в заголовке.

```python
import base64, hashlib, hmac

def verify(secret, headers, raw_body):
    key = base64.b64decode(secret.removeprefix("whsec_"))
    signed = f"{headers['webhook-id']}.{headers['webhook-timestamp']}.{raw_body}".encode()
    expected = base64.b64encode(hmac.new(key, signed, hashlib.sha256).digest()).decode()
    return any(
        hmac.compare_digest(expected, part.split(",", 1)[1])
        for part in headers["webhook-signature"].split(" ")
    )
```

Считайте подпись по **сырому** телу запроса, до разбора JSON: пересобранный из объекта JSON почти наверняка отличается пробелами и порядком ключей, и подпись не сойдётся. Проверяйте и `webhook-timestamp` — доставку старше нескольких минут разумно отклонять.

## Ротация секрета

Секретов у адреса может быть два одновременно, и каждой доставкой подписываются оба — поэтому заголовок `webhook-signature` может содержать несколько подписей. Порядок смены секрета без простоя:

1. добавить второй секрет — приёмник продолжает проверять старым;
2. переключить приёмник на новый;
3. вывести старый из ротации.

Последний секрет удалить нельзя: без секрета подпись не строится.

## Где действует

Пустой список означает «все проекты, каналы и папки, кроме приватных»: событие из приватного проекта или канала уходит наружу, только если он назван в списке явно. Так адрес, настроенный владельцем рабочего пространства, не выносит наружу содержимое приватных мест, в которых сам владелец не состоит.

## Повторы и отключение

- Повтор делается на кодах `408`, `409`, `425`, `429` и любых `5xx`, а также на сетевых ошибках и таймауте (10 секунд на попытку).
- Расписание: 30 секунд, 1, 2, 4, 8 минут — всего до 5 попыток; после этого доставка считается неудачной.
- Три неудачные доставки подряд выключают адрес, владельцу рабочего пространства уходит письмо. Успешная доставка обнуляет счётчик.
- Ответ приёмника читается до 64 КБ, тело ответа не используется — важен только код.

## Требования к адресу

- Только `https`. Приём по `http` возможен лишь на стенде, где это включено настройкой пода.
- Приватные и служебные адреса запрещены: `127.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `100.64/10`, `0/8`, `224/4`, их IPv6-аналоги, а также имена `localhost`, `metadata`, `*.internal`, `*.local`, `*.cluster.local`. Имя проверяется дважды: перед запросом и непосредственно перед соединением, чтобы адрес нельзя было подменить после проверки.
- Редиректы не выполняются: ответ `3xx` считается неуспешной доставкой.

## Если события не приходят

- Адрес выключен — проверьте переключатель рядом с URL и поле «последняя ошибка» на странице адреса.
- Событие не отмечено в списке событий адреса.
- Событие произошло в приватном проекте или канале, которого нет в списке «Где действует».
- Подпись не сходится — почти всегда из-за того, что она считается по пересобранному JSON, а не по сырому телу.
- Ничего не приходило вообще — нажмите «Отправить тестовое событие» на странице адреса: результат появится сразу, а сама доставка попадёт в журнал.
